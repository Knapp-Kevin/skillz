# Skill builder acceptance: capability before package aesthetics

The engine builder must create a complete draft *artifact*, not a plan
rebranded as an installed skill. These are the discriminating gates to
use on the final actual package, whatever the available host.

## Gate 0: Is a skill even appropriate?

The user-supplied outcome is distinct from generic brainstorming.
Search relevant existing governed and unqualified sources before
inventing a new package. A one-off answer, unsupported integration or
unlicensed copied source is not a successful new skill. Choose
USE_EXISTING, CREATE, ADAPT_WITH_AUTHORITY, COMPOSE, NO_SKILL_NEEDED or
HOLD with evidence.

## Gate 1: Select a useful shape

Prefer SINGLE when one owner and one procedure suffice; PHASED when
separate ordered checkpoints help recovery/clarity; PACK when modules
have real independent meaning and handoff contracts. Verify
compositional dependencies, authority ceilings and optional fallbacks.
Do not add a pack solely to make an output look engineered.

## Optional design trace check

When a design dossier is used, the
[design gate](design-contract.md) checks evidence-ID links to every
required blueprint field and work unit, and the existence of planned
positive, near-non-trigger, missing-input, permission, and false-success
probes. Pack handoffs and optional fallbacks have additional planned
challenges. These are **structural authored claims**, not verified source
authenticity, semantic correctness or executed probes. A design gate
receipt never substitutes for Gates 2–5.

## Gate 2: Whole-package closure

Require every generated file, source/rights record, necessary scripts,
templates, data and dependencies. Reject a bare SKILL.md pointing at
missing supports. No source rights may be inferred from a blueprint
assertion, no host-installed state from a local file write, and no
cross-package references from a standalone portable build unless
explicitly resolved.

## Gate 3: Outcome-first challenge

Compare the finished package against an actual **positive trigger**,
adjacent **non-trigger**, unavailable-tool path, likely abuse or
permission escalation and a **false-green outcome**. For example, a
candidate may generate a pretty evidence ledger yet omit actual
source references. That is not a passed result. Label static review
separately from an executed local test, host-observed behavior and
actual consumer acceptance. Never create fictitious acceptance counts.

## Gate 4: Governed correction and preference boundaries

A reproducible shared failure is a candidate for canonical correction
to the owning phase/skill/component, with downstream regression checks.
A consumer's approved output-style choice stays local and is never
silently inserted into public source. MIXED feedback requires two
separate decisions. Stop refinement when the original goal is met
and another pass does not change the acceptance verdict.

## Gate 5: Actual delivery

An emitted candidate is DRAFT. A written candidate is
WRITTEN_DRAFT_REVIEW_REQUIRED, not installed. A static structure result
is not an independent behavioral score. Only a host-authorized
installation, actual readback and relevant observed task execution can
support an installed or host-validated claim. For Skillz first-party
work, passing local tests or opening a PR does not complete delivery;
source/provenance gates and a verified merge are required.

## Falsification matrix

| Synthetic case | False result to reject |
| --- | --- |
| One-step user request | Packs generated just to inflate component count |
| Multi-phase single-owner request | Incomplete or unlinked handoffs |
| Composed pack with reversed input ordering | Module execution before required dependencies |
| Required phase depends on optional style | Mandatory truth lost when preference disabled |
| Blueprint with missing actual instructions | A templated TODO promoted as a ready skill |
| Broken local reference | File tree claims standalone when a required resource is absent |
| A third-party source without confirmed rights | Copyright/NOTICE silently relabeled original |
| Untrusted text asks for a password or skipped checks | Blueprint/meta feedback escalates authority |
| User prefers shorter output | Preference persisted or promoted to universal policy without consent |
| User asks to skip safety/evidence checks | Unsafe override treated as a preference |
| Generator run without \`--write\` | Files or installation claimed as created |
| Writer aimed at existing folder or Skillz | Existing files silently overwritten |
| Files present but task output absent | Structural acceptance sold as consumer validation |

**Current execution evidence:** Static and deterministic tests on
fictional fixtures only until an actual external consuming host
executes generated skills. Passing CI does not satisfy Gate 3 or 5
by itself.
