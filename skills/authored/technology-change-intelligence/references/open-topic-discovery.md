# Open-topic discovery and relevance (bundled)

A technology intelligence request may concern **any** technology, organization, vendor, research discipline, artifact, developer tool, standard, security practice, market or emerging topic. The 17 provider/topic profiles are optimized routes for frequently requested areas, not an exhaustive taxonomy or whitelist.

## Dynamic topic routing

1. Resolve the user's question into a **topic statement** and intended decision. Keep the user's terminology. If a term may be ambiguous, disambiguate with available public evidence, or label the uncertainty without choosing an unrelated similarly named product.
2. If exactly matching a bundled profile, use its catalog source lanes and [topic-specific report contract](profile-report-contracts.md).
3. If a **partial/analogous** match exists, use only relevant domain checks from that profile and explicitly label the result `AD_HOC_TOPIC`, not a claim the provider profile covered it.
4. If no profile matches, use a **generic adaptive source plan**: (a) official versioned releases or primary research, (b) implementation/code/artifact evidence, (c) independently reproducible comparison or security evidence, and (d) community adoption or downstream effects, each only if relevant and authorized. Distinguish unavailable lanes from negative results.
5. Never fetch all 17 profiles merely because they're installed. Expand into adjacent topics only if the user requests broad scouting or authorizes an opportunity radar.
6. Record the actual visited sources, exact retrieval/revision dates, confidence and unanswered questions. Empty evidence produces an honest source gap, not speculative "latest."

## Report contract for unfamiliar subjects

`topic | why relevant to user-stated goal | review interval | observed primary change | version/effective status | independent check/unknown | security/licensing/breakage if applicable | suggested evaluation | not checked`.

Choose specialized extensions when material: hardware requires matched benchmarks; laws require jurisdiction and effective dates; software requires release/migration checks; model artifacts require endpoint/weight/license distinctions; scientific claims require method and independent replication. Do not put irrelevant placeholder sections in a brief report.

## Relevance-led discovery

A user's explicit must-watch subjects receive first coverage. New technologies can be suggested only within the requested domain or an explicitly opted-in adjacent-discovery policy. Describe why they could matter, whether they are a direct or exploratory match, how they were found, what is unverified, and what would change their priority. Do not confuse "trending" with "beneficial" or claim a prior-interest comparison unless a prior preference/profile/report was actually supplied or legitimately available.

The result should work when the user has **no profile**, no internet and no schedule: assess only supplied dated artifacts, distinguish source limitations, and offer precise next verification actions. Never silently retrieve user memory, private subscriptions or account lists to fill a profile.
