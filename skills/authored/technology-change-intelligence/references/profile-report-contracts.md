# Topic-specific technology intelligence deliverables

These sections are independently authored outcome specifications, not copied historical templates. Load with `profile-catalog.json`. This file governs **report usability**, while `event-evidence-contract.md` governs claims and provenance. Section headings are flexible, but preserve each section's distinct decision purpose; if there are no supported events for a section, use `NO_VERIFIED_CHANGES` or `NOT_CHECKED`, not invented news.

For each selected profile, present the sections in order where the requested purpose warrants them. Keep the shared dated event/source ledger available as an appendix. Avoid rendering seventeen sets of empty headers in a cross-profile report: each selected profile's topical coverage and meaningful unknowns still must remain traceable.

## Discovery and decision constraints

- GitHub discovery requires distinct **new** and **gaining-traction** populations. Record the query window and evidence for each; repository existence, star change, actual active development, license and independent verification are different attributes. For a broad discovery request, lead with a **short one-line-per-repository** scan grouped as recently created versus older gaining traction and, where useful, by AI/LLM, agents, MCP and developer tooling. Each line must preserve a factual creation/activity cue, a source/status cue, and key license or safety UNKNOWNs; never invent unavailable metadata to fill it. Keep detailed evidence in a compact appendix or on-demand drill-down rather than forcing a long repeated event table into the primary scan. If the user asks for comparative depth, expand without a fixed item/analysis cap. Offer at most three deeper-investigation candidates with why and what remains unknown. Do not automatically add to a registry or contact authors.
- Research-focused profiles should distill method/architecture implications and reproducibility rather than listing abstracts without interpretation. Framework/API developments belong in distinct sections from papers and social reception.
- Model publishers must separate checkpoint/weight availability, licensing, hosted API and end-user feature access. Dated sources determine which of those is actually established.
- Security/protocol/governance topics put effective obligations, breaking compatibility and verified risk above speculative ecosystem noise. An advisory is not a deployed patch; a policy proposal is not an enacted rule.
- Time and cost constraints stay host-local. A user request for weekly or monthly intelligence does **not** itself create a schedule or permit future private data access. A separate authorized host workflow can accept an explicit recurring instruction only after it establishes cadence, time zone, start/stop, sources, future connector permissions, delivery scope, retention, cost and revocation. This skill is read-only and must never invoke a scheduler or infer recurrence from a prior reference's former behavior.
- Mark per-profile coverage explicitly: official pages checked, research/artifact repositories checked, independent community evidence checked, any material unavailable lanes, and the actual local-calendar window. A profile's declared watch list is not proof those sources were visited.

## Semantic qualification

Each profile is an independently testable mode, not one seventeenth of a shared PASS. Equivalent source access, source-date pinning, scenario difficulty, observed outputs, report completeness and non-trigger behavior are required before asserting parity. The 1.5x target needs scored paired host-agent outcomes and must not be inferred from the presence of this file.
