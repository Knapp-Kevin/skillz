# Specialist execution gates: 17 topic routes

This document belongs to the downloadable Technology Change Intelligence package. It adds **operational decision checks**, not another set of generic report headings. Apply only selected profiles. It does not authorize tools, private reads, scheduling or writes; the entrypoint's evidence and authority requirements always apply.

## How to use these gates

1. Identify the exact request, including **which interface or artifact** could change the user's decision. For named routes, load its catalog row, its report contract and the matching gate below.
2. Collect each material source lane independently within the authorized scope. A **source lane not checked** stays `NOT_CHECKED`; don't turn a suggested search into an assertion that it ran. Prefer dated origin artifacts to a syndicated announcement. If an optional connector exists, use it only when the user and host authorize that read; ordinary browsing is a legitimate fallback.
3. For each claimed change, state **what can be concluded**, **what remains uncertain**, **what test or evidence resolves it**, and **whether action is justified now**. Separate an announcement from a released version, available entitlement, deployed fix or measured performance.
4. Where the user provides a bounded technical target or a **redacted and explicitly approved** project summary for this one request, return a **target relevance verdict**: `APPLIES`, `MAY_APPLY`, `DOES_NOT_APPLY`, or `UNKNOWN`, plus affected surface, version/condition, evidence and safe next check. Never infer a target from private memory or silently open repositories, configurations, profiles or local files.
5. Distinguish real changes from repeated coverage. Use a short **patterns and contradictions** synthesis *only* when supported by multiple identifiable events; community popularity alone cannot establish independent confirmation.

| `meta-llama` | Do the particular weights permit the intended deployment and redistribution? | Quote no blanket license conclusion: check version-specific use, restrictions, weight access, runtime fit and separately verified quantization performance. |

| `mistral-models` | Is the announcement an API model, a weight checkpoint, a developer tool or a licensing update? | Separate hosted access, versioned weights, actual usage rights, SDK changes, prices and independent performance; identify migration effects before commentary. |

## Sparse-evidence fallbacks

- **No browsing or connector:** report only dated user-supplied source facts and `NOT_CHECKED` for current external lanes. A synthetic packet is never presented as real news.
- **No events in one lane:** `NO_VERIFIED_CHANGES` means that lane was examined with an adequate documented method; otherwise use `NOT_CHECKED`. Don't confuse the two.
- **No authorized target:** deliver generic impact analysis, with explicit required target fields if the user asks for a compatibility verdict.
- **Conflicting records:** retain both, identify the governing artifact and propose a low-risk discriminating check; no invented winner.
- **Incomplete profile coverage:** include a compact coverage ledger (lane, checked time, source class, result, limitation), not a blanket claim that the entire provider was examined.
- **Cross-profile overlaps:** preserve distinct profile sections but link a shared underlying release to one canonical event identity. Repetition is not an additional independent source.
- **Interesting but unverified lead:** include as `INVESTIGATE`, never a production deployment/installation or subscription recommendation.

## Portable report closure

Finish the chosen report with `Decision now`, `Target relevance` (if applicable), `Verification next`, `Patterns / contradictions`, `Coverage and NOT_CHECKED`, and `Sources`. The specialized topic sections in `profile-report-contracts.md` remain required; do not replace them with this closure. Only the selected profiles are evaluated, not all seventeen.
