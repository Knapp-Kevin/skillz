## Evidence for a much larger discovery universe

**GitSkills**, a peer-reviewed research dataset with a [2026 preprint](https://arxiv.org/abs/2608.10906) and [2026-08-10 Zenodo release](https://zenodo.org/records/21875637), reports a **July 2026** public-GitHub collection of **3,797,117 SKILL.md file occurrences in 282,200 repositories**, grouping into **1,877,981 exact content hashes**. This is a public-GitHub research **lower bound**, not a verified pool of independent, suitable, safe or correctly licensed skills; repository copies, autogenerated templates, invalid front matter and misleading names occur. The dataset documents 7,264,865 sibling-file observations and separate repo metadata.

- Source-discovery inputs, **not canonical authoritative skill publishers**: [GitSkills Hugging Face Parquet mirror](https://huggingface.co/datasets/mvaccargiu/gitskills), [smaller GitSkills sample](https://github.com/giuseppedestefanis/gitskills-sample) (sample documents 13,000 content hashes across 11,841 repositories), [skills.sh directory](https://skills.sh/) and targeted GitHub/creator repositories.
- GitSkills dataset mirror advertises **CC BY 4.0 for dataset metadata**. That license does **not** relicense original `SKILL.md` files, creator works, models, bundled code or trademarks. Inspect original source terms and package-local rights before verbatim reuse.
- Keep bulk research data in the research host if needed, NOT as a multi-GB committed repository snapshot. Save only bounded passive, verifiable source/identity/rights receipts to skillz. Do not store visitor history, tokens or private data.

## Discovery campaign: evidence-first, open-ended

1. **Harvest source-family leads across independent routes.** Search GitSkills repo/owner data and distinct content groups, GitHub source-native search, current directories and creators. Include community collections, first-party provider catalogs, professional-domain skills, multilingual and regional creators, tool-specific skills, coding and non-coding agents, and independent skill design approaches. Do not favor first-party sources. Revisit already indexed authors for fresh versions and new material.
2. **Dedupe before expansion.** Crosswalk canonical repo/owner/immutable revision, source mirrors, forks, aliases, generated distributions, nested role, exact `SKILL.md` content SHA and **complete package-tree SHA**. Content-hash equality does NOT prove complete package identity; different packages can bundle different executables despite identical entrypoints. Count distinct methods separately from filenames where evidence permits.
3. **Measure capability coverage rather than volume.** Map independently observed methods to the current 33-domain/247-subdomain directory, with multiple alternatives for substantive gaps. Surface *new mechanisms* and cross-domain transferable procedures; name-only matches are leads, not semantic review. Document sparse coverage and where discovery should go next.
4. **Preserve controlling rights.** Each promising source receipt has original owner/repo, exact revision, canonical path(s), declared root and per-package licenses/notices when inspected, restrictions (`NOASSERTION`, NC, share-alike, commercial, proprietary), sidecar rights, and actual source evidence URLs. No content may inherit skillz's MIT license.
5. **Separate evidence tiers.** `SOURCE_DISCOVERED` → `IDENTITY_VERIFIED` → `COMPLETE_PACKAGE_STATIC_REVIEWED` → independently recorded package-security state → `BEHAVIORALLY_VALIDATED` only with executed evidence. None automatically conveys rights/authority or install eligibility. Keep DEFER for missing or unresolvable source evidence, not invented PASS.
6. **Publish reviewable slices.** Each tranche should cover a distinct, verifyable source set with stable data, objective provenance and archival URLs, machine-readable lead indexes, a human summary, and no stale shared-file overwrites. Integrate into capability-first navigation instead of burying candidates in archive links. Use `[skip ci]`, respect existing GitHub Actions budget, no repository-owned scripts/automation.
7. **Prioritize by marginal insight.** Favor independent creators, under-covered capabilities, differentiated implementation patterns, useful safety/validation boundaries and genuinely reusable methods. A low-quality or repetitive source can still be a research lead, but not a recommended skill. No fixed file-count target or declaration of ecosystem completeness.

Distinguish newly discovered source leads from inspectable, security-cleared packages. If it has no prior snapshot/history, mark the difference UNKNOWN rather than inventing an evolution story.

**No silent installation, dependency execution, provider access, private-data disclosure or writes.** User history informs host-local recommendations only.
