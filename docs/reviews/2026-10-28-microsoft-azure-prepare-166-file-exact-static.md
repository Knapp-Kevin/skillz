**Strengths.** Clear azd-specific trigger boundaries; plan approval before Phase 2; subscription/location confirmation; validation-before-deployment intent; non-destructive workspace rules; Entra-only SQL Bicep; managed identity and Key Vault guidance; two-phase ACR/Container Apps deployment; detailed Functions recipes, cold-start and regional quota planning; rollback-oriented guidance. These are useful bounded design mechanisms.

**Decisive failures from exact source material:**

1. **Mandatory plan-file overwrite hazard.** Root `SKILL.md` line 31 mandates writing `.azure/deployment-plan.md` as the *first action*, before examining existing files. Its own `references/global-rules.md` lines 7–16 classifies overwrite as destructive and requires `ask_user`. The workflow has no existing-file inspection or path-specific approval before that first write.
2. **Nested deployment bypass.** `references/services/app-service/templates/recipes/README.md` lines 57–61 prescribes `azd provision --no-prompt` and `azd deploy --no-prompt`. `references/services/functions/templates/recipes/composition.md` lines 38, 79, 207 and 213–215 prescribes `azd up --no-prompt` or direct provisioning/deployment. `references/services/app-service/templates/web-api.md`, `web-app.md`, and `references/services/functions/templates/README.md` likewise show direct `azd up --no-prompt`. These operational branches contradict the root's explicit `azure-prepare → azure-validate → azure-deploy` boundary and lack action-specific approval for billable resources, traffic and RBAC.
3. **Secret-value disclosure.** `references/services/key-vault/sdk.md` lines 16–17 retrieves a Key Vault secret and prints `secret.value` to output. `references/recipes/azcli/commands.md` lines 86–90 passes `<secret-value>` as a CLI argument. These are unsafe patterns for real credentials even though other references advocate managed identity and avoiding hardcoded secrets.
4. **Security-control broadening.** `references/services/durable-task-scheduler/README.md` lines 61–65 recommends `ipAllowlist: ['0.0.0.0/0']` and an equivalent CLI update to fix 403 errors. Broadening access is a security-control mutation, not a routine diagnostic; it requires owner-scoped approval and a narrower alternative. The same branch describes role grants to both application and deploying-user identities.
5. **Persistent SQL permissions.** `references/services/sql-database/scripts/grant-sql-access.sh` lines 66–99 creates a database principal and grants `db_datareader`, `db_datawriter` and optionally `db_ddladmin`. The PowerShell sibling has the same operational purpose. These scripts may be legitimate after explicit target/database/role authorization, but the recipe does not establish that boundary itself.
6. **Environment and provenance risks.** `references/resources-limits-quotas.md` lines 39 and 53 directs Azure CLI extension installation without a distinct host change approval. `references/runtimes/nodejs.md` contains a development-secret fallback and sample secret-in-environment command that must not be copied into production. Bundled `eval/summary.md` examples with PASS rows are source-authored example evidence, not independent behavioral validation of this candidate.
