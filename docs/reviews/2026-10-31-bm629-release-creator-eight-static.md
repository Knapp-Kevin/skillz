## Source-family synthesis
1. **Differentiated methods, shared boundary problem.** The release author/reviewer pair provides concrete rollback and go/no-go quality bars. The content-template gateway and skill forge are persistent authoring orchestrators; the sanitizer is an input-trust guard with a durable incident ledger. OpenAPI generation, polyglot hooks and uv workspace architecture address different engineering concerns. These are not duplicate prompt wrappers, but seven of eight escalate from guidance into effects without separately established authority.
2. **Release distinction.** `reviewing-release-runbook` is a useful read-only document gate. Its `VERDICT: approve` is approval of *document quality only*, not permission to deploy. The authoring twin's optional but imperative staging rehearsal, failure injection, user-facing status communications and private-architecture research require independent environment, data, disclosure and communication authorization. A rehearsal labeled an aid is still a real external action if performed.
3. **Persistence and secret-bearing identifiers.** `external-content-sanitizer` strips URL query strings in displayed responses yet explicitly retains full original identifiers in `docs/security/flagged-sources.md`. This may persist credential-bearing URLs, sensitive file paths and private identifiers without retention or access scope. The safety invariant is therefore incomplete; preserve the never-echo and category-based detection concepts, not the unbounded logging behavior.
4. **Template and skill-generation authority.** `content-template-gateway` imposes a universal mandatory template and creates persistent research/template/index files as a side effect of ordinary content drafting. `skill-forge` writes auto-loadable skills, may run generated scripts and can append to a caller agent file. Neither a knowledge gap nor a request to draft a message grants those writes, external research disclosure or script execution. Forge popularity filtering is source context, not quality.
5. **Engineering mutations.** `openapi-ts-client` installs packages, generates files and proposes CI drift changes; `polyglot-git-hooks` enables persistent `.git/hooks` installation and auto-fix/re-stage behavior; `python-monorepo-architecture` directs code relocation and optional CI contracts. All are useful adaptation/checklist methods once actual mutation scope and dependencies are authorized. Their pinned June/May research does not prove current upstream package/API freshness.
6. **Dependencies and exact identity.** Eight source packages contain **30 files**, including source-owned reference documents. No bundled upstream code was copied into `skillz`; no package security scan or external behavioral test was run. All eight behavioral states remain `not-run` and semantic VERIFIED does not imply unchanged-use or deployment authorization.
7. **Remaining ten:** provider-operations **5** (`atlassian-rest-ops`, `cloudflare-pages-ops`, `github-cli-ops`, `jenkins-rest-ops`, `netlify-ops`); document-discovery **3** (`project-document-discovery`, `reviewing-document-discovery`, `reviewing-document-set`); engineering **2** (`sql-job-queue`, `token-optimization`). The provider set has infrastructure, credentials and external side effects and should be deep-reviewed separately. The document-discovery producer has bundled scripts/schemas and private-file exposure, so do not force a quota.
