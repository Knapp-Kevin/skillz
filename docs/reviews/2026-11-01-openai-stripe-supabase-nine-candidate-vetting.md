## Macro synthesis, omission/freshness defects and user fit

1. **Financial and data authority:** Stripe's Connect recommendation asks confirmation of *design choices*, while Stripe Apps and Projects automatically scaffold/upload/accept TOS or mutate resources. Supabase's SQL-first iteration similarly treats a connected MCP as execution authority. These are hard unchanged-use failures, regardless of official authorship. Stripe Directory's explicit price/approval flow is a positive mechanism, but does not cover all network and privacy exposure.
2. **Secret/privacy boundary:** Prefer vault or secure external credential paths; do not request real API keys in chat or include credentials, token fragments, signed URLs, customer/merchant data, private logs, or SQL row contents in review evidence. Illustrative sk_test_xxx and password 'xxx' are placeholders, **not observed live secrets**, but must never become real inlined values.
3. **Same-pin freshness:** Two separate official plugin copies of Stripe/Supabase disagree about API date and package version. Exact tree and SKILL blob, not name or vendor, determine provenance and disposition. Do not call either copy “latest” without independent live documentation verification.
4. **Reference value:** Stripe fee/liability compatibility and tax-registration checks, restricted keys and webhook signature patterns, Supabase RLS and Postgres indexing are differentiated. Extract/checklist/composition can be useful; none of the nine receives unchanged-use approval or an admitted semantic pair.
5. **Source-family priority:** These two finite plugin families are now resolved at this discovery pin; further similarly branded wrappers are lower priority than qualifying the 36 existing first-party repair trees and finding genuine admitted-source provenance gaps. No new architecture is justified.
